# Liquipedia 赛制显示（本地开发）

赛事进程 Tab 以移动端优先的紧凑表格与带晋级连线的对阵图，展示赛季绑定的 Liquipedia 排名与对阵；瑞士轮默认展示逐轮结果，可收起。页面不展示规则、原文、更新时间及来源说明，队伍详情页也不展示 Liquipedia 外链。既无手动来源也无法自动识别来源的赛季显示“暂无赛事进程”，仍可通过比赛列表查看已收录的比赛。独立的 `tournament_snapshots` 表持久保存来源快照，后台自动同步，不修改比赛和战队数据。

旧积分榜组件及后台的模板、晋级名额、积分榜阶段编辑、隐藏队伍和手动排序配置已移除，保存赛季可视化配置时不再提交 `standings`。已有配置中的旧字段不再读取，下一次保存该赛季配置时移除；本次不批量清理数据库。`season_stages` 及阶段接口继续供公开 API、阶段统计和离线导出使用，战绩统计接口继续供战队详情和选手赛季轨迹使用。

## 本地预览

需要 `backend/.env` 配置的本机 MySQL。以下服务只创建/使用 `tournament_snapshots` 表，其他业务数据仍代理线上公开 GET；不会启动 Matchweb 同步、完整数据库初始化或向线上写数据。预览强制数据库地址为 loopback：

```powershell
node backend/scripts/preview-tournament.js --port 3012 --source-cache .local/tournament-sources
```

另开终端启动前端：

```powershell
$env:API_PROXY_TARGET='http://127.0.0.1:3012'
npm run dev -- --host 127.0.0.1 --port 8083 --strictPort
```

- 中国赛区第二阶段：`http://127.0.0.1:8083/visualize?seasonId=13&tab=overview`
- EMEA 第二阶段：`http://127.0.0.1:8083/visualize?seasonId=20&tab=overview`
- 世界杯小组赛：`http://127.0.0.1:8083/visualize?seasonId=24&tab=overview`
- 世界杯季后赛：`http://127.0.0.1:8083/visualize?seasonId=25&tab=overview`
- 尚未开赛的 NA 第三阶段：`http://127.0.0.1:8083/visualize?seasonId=30&tab=overview`

可选 `--source <seasonId>=<url>` 只覆盖预览服务的来源，不回写线上配置。生产代码优先从 `visualize_season_<id>.liquipediaTournamentUrl` 读取；缺省时通过标准 OWCS 赛区/阶段名称或已知国际赛事标识解析对应的 MediaWiki 标题，实际拉取并解析成功后才展示。韩国赛区使用 `Asia/Stage_N/Korea` 路径。未知名称不做模糊搜索，手动链接永远优先。可选 `--source-cache <目录>` 用五分钟内真实 API 响应加速本地冷启动，过期仍请求来源。旧 `.local/tournament-preview-cache` 中的完整快照自动填入尚无快照的数据库记录，后续以数据库为准。

## 数据流与维护

1. `GET /api/seasons/:seasonId/tournament`，以及展示版 `/api/site/v1/seasons/:seasonId/tournament`，只读取数据库快照，再按当前赛季及来源文章完全相同的关联赛季的站内记录绑定跳转。访问页面不会发起来源请求、读取旧文件或写数据库。浏览器不能指定任意上游地址或匹配赛季范围。
2. 使用现有固定 Overwatch MediaWiki API 客户端，读取 `action=parse` 的 HTML。解析阶段结果区的详细赛程链接和赛事导航，保留链接原始标题层级；规范化带锚点的链接，在同一赛事范围内最多读取 12 页、向下 3 层并防止循环。主页可以只有导航；目标页重定向到其他赛事或必要子页读取失败时保留上次完整快照。参赛资格说明不作为详细赛程链接，同级预选赛只有在主页面明确包含该阶段或直接配置该阶段来源时才读取，导航不能继承上一个页面的常规赛身份。未知阶段、关联冲突及遍历限额记入 `discovery.diagnostics`。
3. `LiquipediaTournamentParser` 识别 Swiss / group-table / brkts 模板。排名使用来源当前选中周次的表格，保持同分排序。轮次翻译为中文。后端仍保留规则译文与原文，前端不展示；规则翻译使用模板和预置译文，未认识的规则保留原文，不交给生成模型猜测。
4. 主、子页重复的表格和对阵在同一阶段、小组内去重；不同阶段即使积分相同也分别保留。抓取和前台共用 `tournamentSemantics.mjs`，并在读取旧快照、离线导出时补齐阶段身份。后端保留模板内的晋级树结构，展示端按晋级关系自动排布紧凑双行比分节点，三列对阵适配手机宽度，更多轮次仅在图内横向滚动。季军赛单独显示，不需要配置坐标。未支持的对阵树保留解析到的比赛供匹配，前台只绘制支持的表格和对阵结构。
5. 队伍严格优先按保存的 Liquipedia 页面和 API 确认的重定向，在全站队伍目录中识别，不要求预先关联赛季：页面唯一对应一支本地队伍即采用，不受其他队伍的同名或别名影响；多支队伍绑定同一页面则拒绝匹配，不再用名称猜测。页面未找到对应队伍时，才在当前赛季已关联或允许匹配范围内有比赛出场记录的队伍中，尝试精确主名/别名/来源短名；名称必须唯一，且双方都保存了链接时不能指向不同页面。识别队伍不会自动创建赛季关联或比赛。
6. 比赛按两队身份、北京时间日期 ±1 天以及已完成比分核验。默认仅查当前赛季；若多个本地赛季解析到完全相同的来源文章（如世界杯小组赛、季后赛），服务端才加入这些关联赛季。手动来源配置优先，不按同级路径、共同父目录或相似赛事名扩大范围。链接携带实际比赛的 `matchSeasonId`，逐轮、逐场及对阵图统一使用，线上读取、预览与离线导出一致。同队再战按候选关系整组求解一对一对应：只有在所有完整对应方案中都唯一确定的比赛才链接；无完整方案、有来源冲突或仍有多解的比赛保持未链接，不按最近日期或列表顺序猜测。重复来源必须比分一致，跨阶段候选分别核验。站内比赛记录和队伍链接变更不必等待来源缓存刷新。
7. 瑞士轮单元格的比分与对手标识居中排列，整个结果区域可点击。单元格依据同一来源页面或其子页中的轮次、双方身份与比分，关联到已核验的站内比赛；同一比赛在双方队伍行中链接一致。没有比赛、尚未匹配或存在歧义时仅显示结果。

## 赛事阶段切换

赛事进程按实际阶段显示标签，一次展示一个阶段；阶段 Tab 紧接上级 Tab，位于内容滚动区之外，与赛事数据分类 Tab 同层。只有一个有内容的阶段时也统一显示阶段名与日期。阶段根据来源的 Format 顶层赛制、标题层级和子页语境划分，不根据表格或对阵图的数量划分，也不依赖赛季 ID。

阶段导航直接复用站内 `DetailSectionTabs`，与“赛事数据”分类栏保持相同的白底、橙色斜块、淡色选中底和正文排版。手机端紧接主导航全宽显示，四个阶段也放在同一行；较长名称显示为“种子决定战／最后机会赛”，悬停提示和无障碍名称保留完整阶段名。每个 Tab 的阶段名下方展示该阶段日期；内容区不再重复阶段名和通用表名，仅保留 A/B 组等必要分组标识。瑞士轮“逐轮”开关放在队伍列表头内，不另占一行。不带日期的其他详情 Tab 保持原有单行样式。

日期来自来源 Format 对应阶段的起止日，年份取自赛事文章；按原始日历日期展示，不经浏览器时区转换。支持同月、跨月、跨年和单日日期；同一天进行的不同阶段分别保留。旧快照的赛制原文可直接解析，不需要另抓来源。

单阶段也展示日期。来源缺失、日期无效或同一阶段存在冲突日程时显示“日期待定”，不把已抓到的首末场比赛当作完整阶段边界，不把整个常规赛日期分配给其中的瑞士轮子阶段。阶段对象保留 `dateRange.startDate/endDate` 及原始赛制文本以供核验。

- 世界杯 A–D 组、巴黎季中冠军赛 A/B 组统一归入“小组赛”；即使小组使用双败对阵图，也不会被误分到季后赛。季军赛保留在“季后赛”。
- 中国赛区为“瑞士轮／循环赛／季后赛”；瑞士轮积分、逐轮比赛与种子决定战属于同一阶段，循环赛积分及周赛程归入循环赛。
- 北美、欧中非为“常规赛／季后赛”。韩国来源明确列出的“季后赛种子决定战”和“最后机会资格赛”单独保留；韩国的种子决定战不会被归入中国赛区的瑞士轮。
- 已有积分表或对阵图的阶段保持紧凑展示；只有比赛列表的阶段仍显示比赛卡片。未公布内容的阶段不创建空标签，无法确认归属的内容保留在“其他赛程”。

新解析保留 `sourceHeadings` 完整标题路径，旧数据库与离线快照仍可根据保留的原文标题、赛制和子页路径归组，无须等待重新抓取。旧快照的 Playoffs 标题在展示时统一为“季后赛”，不改动来源原文。

`tournamentStage` 查询参数优先指定阶段，例如 `?seasonId=13&tab=overview&tournamentStage=swiss`、`round-robin`、`playoffs`。有效选择在刷新和从比赛详情返回时保留。未指定或阶段无效时，按北京时间的日历日期默认显示正在进行的阶段；阶段间歇显示接下来最早开始的阶段及其可用前瞻，全部结束后停留在最后结束的阶段，全部尚未开始时显示最早开始的阶段。起止日期均包含当天。多个阶段同时进行或下一阶段开始日期相同时按来源顺序选第一个，结束日期相同则选顺序靠后的阶段。缺少或无效日期不参与时间判断，全部日期不可用时回退至首个有内容的阶段。页面每分钟重新检查时间，手动选中的阶段不会被覆盖。切换保留阅读位置，支持方向键、Home/End 和屏幕阅读器。

## 普通积分表逐场结果

赛事进程加载时沿用比赛列表的居中转圈与简短提示，显示“正在加载赛事进程”“稍后即可查看赛制与对阵”；减少动态效果时保留静态状态标识。三场前瞻以 44px 高的小圆角卡片铺满一行，日期居中，下一行双方队标对称放在左右两端，中间显示队名与 VS。当前阶段可查看前瞻的未开赛比赛去重后超过三场时，在第三张卡片右侧叠加边缘渐隐模糊和箭头“查看更多”，不为入口单独预留空间；入口宽 48px，点击或键盘激活后切换到当前赛事的比赛列表 tab。

赛事进程的逐场单元格、瑞士轮单元格、对阵图及纯比赛列表统一使用 `tournamentMatchNavigation.mjs`。双方已确认本地身份、开赛时间在未来、没有已打比分且来源无冲突时，可直接进入站内前瞻；待定队伍或时间不生成前瞻链接。未来的本地 0:0 占位比赛也可进入前瞻，已有赛果的记录继续进入比赛详情。前瞻参数携带双方 ID、实际开赛时间及返回赛季/阶段，双方队伍行复用同一场比赛的原始方向，避免生成两个不同前瞻。前瞻统计优先按 ID 读取，旧会话里其他日期的同队对阵不能补入当前比赛身份。

阶段内容顶部仅横向一行展示最近 3 场可查看前瞻的对阵和北京时间，不显示区块标题；切换赛季、阶段时重新取最近 3 场。手机端同样保持三张卡片同排，完整队名与“查看前瞻”保留在链接说明中。同一比赛在双方积分行或多个来源块中出现时，按赛季、双方 ID 和时间去重，同队不同时间的再次交手仍分别展示；“查看更多”使用去重后的完整数量判断，待定队伍、时间缺失、已赛比赛不计入。积分表的逐轮单元格用北京时间日期替代未开赛场次的空比分位；已有比分的场次只显示比分，日期不重复出现。对阵图在卡片上方的单行标题中左侧显示轮次、右侧显示“月.日 时:分”；手机端仅缩写重复的“组”“赛”等轮次用字，完整名称仍在标题提示和链接说明中，三列能同时显示时不强制滚动。纯比赛列表把时间放在卡片上方。已确认双方身份的未开赛比赛仍可点击进入前瞻；瑞士轮来源时间按同一来源轮次与唯一对阵核验，不用同队组合猜测。

`node scripts/verify-tournament-previews.mjs` 检查韩国真实完整常规赛前瞻、日期在空比分位、320/390px 布局、顶部提示、刷新和返回阶段；中国已赛瑞士轮核对比分不被日期替代；对未来已知双方的对阵图及纯列表使用明确隔离的浏览器响应样本。当前真实韩国赛制含 36 场常规赛、72 个双方视角单元格，均可进入对应前瞻；实际季后赛仍为 TBD，不提供无效链接。

比赛列表的未开赛比赛也使用 `GET /api/seasons/:seasonId/tournament` 已解析的赛事来源。无需手动填写链接；已填写时仍优先生效。筛选只接受来源主页及快照 `sources` 中已发现且无阶段冲突的子页，忽略周次锚点，不把所有同前缀页面当作同一赛季。因此韩国 `Korea/Regular_Season#Week_N` 可进入对应韩国赛程，未确认的同级预选赛和其他赛区仍被排除。来源快照尚未就绪时按接口建议重试；接口暂不可用时保留手动来源的精确页面匹配。切换赛季或离开列表后，旧请求不能覆盖当前列表。

本地回归脚本 `node scripts/verify-upcoming-schedule.mjs` 检查真实韩国待赛列表及前瞻跳转，并用仅存在于浏览器的响应验证空配置、手动主页配置及预选赛/其他赛区排除；不会写入线上配置或比赛。

比赛日选择器按比赛周分组，优先读取赛事快照的 `Week N` 标题及赛程链接的周次锚点，不按月份或周一至周日截断。已结束的赛季同样读取赛事快照，只有未开赛 ticker 的请求受赛季状态控制。来源时间换算为页面比赛日期后仍保留来源周次；已关联的本地比赛沿用来源周次并保留原始日期。完整来源赛程参与划分，但仅渲染列表中可选择的比赛日，避免待赛数据只剩部分日期时周次重排。没有周次信息时，按连续比赛日归组：允许中间休息一天，连续两天无比赛则另起一组；单组最多涵盖七个日历日，以实际首个比赛日为起点。所有分组保留已确认的阶段名称，例如“常规赛 · 第 1 周”“瑞士轮”“季后赛”，阶段改变时另起一组；同日多个阶段并列显示名称，日期按钮仍只有一个。已关联的本地比赛身份优先于碰巧同日的其他阶段来源时间。只有阶段也无法确认时才标“比赛周”，不伪造官方周次。日期按钮显示月、日，跨月和跨年仍可放在同一比赛周；未知日期独立放在末尾。`node scripts/verify-schedule-stages.mjs` 覆盖历史赛季的快照请求、阶段名称、比赛日完整性，以及来源加载失败时保留本地赛程。

国服循环赛、欧美和韩国常规赛、世界杯各组，以及已有积分表的种子决定战，可从同阶段、同小组的比赛列表生成每队的逐场结果。按已确认的来源队伍页面（含重定向）定位，不以队名相似或相同对阵跨阶段拼接；站内没有比赛详情时仍可显示来源比分。列表按比赛时间排序，比分始终从该行队伍的角度显示。不同日期重赛分别保留，主子页重复展示只计一次。

原积分、排名和净胜局继续来自来源表格。逐场汇总与表中胜负、小局交叉核验，明确单／双循环赛时检查每队场次和交手次数；韩国种子决定战按来源规则扣除常规赛基线作校验，保留表上累计积分。缺少部分比赛时只显示已确认赛程，列名使用“已知 1”等并显示“部分赛程”；未知阶段、无法唯一归属、顺序歧义或比分冲突时保留积分表。TBD 对阵保持未知，不填零或猜测对手。

逐场开关位于队伍列表头，每张表独立收起／展开，不增加工具栏。沿用瑞士轮的比分与队标单元格，手机端只在表格内部横向滚动并固定队伍列；阶段 Tab 保持 40px 的两行样式。

## 队伍多个来源页面

后台队伍编辑中的 Liquipedia 页面支持逐条添加、修改和删除。`teams.liquipediaUrls` 保存规范化、去重后的页面数组；第一个有效链接同时写入旧 `liquipediaUrl`，兼容旧客户端。现有数据库只增添可空 JSON 列，旧记录的单链接会自动作为列表内容读取，不更改队伍 ID、名称或历史比赛。

新客户端提交 `liquipediaUrls` 时以整个列表为准，空数组清空全部链接；省略链接字段时保留原值。旧客户端仅提交 `liquipediaUrl` 时只替换主链接，保留其他页面。保存时按 ID 顺序锁定队伍目录并检查全部主/附加链接的占用，冲突会返回所属队伍名称；不会请求 Liquipedia。已确认的 API 重定向仍在赛制匹配阶段参与规范化，若造成多队命中则拒绝关联。

赛事积分、公开队伍 API 和离线导出均识别所有绑定页面。改名不影响已绑定页面；不同分队是否归入同一本地队伍由管理员确认，不根据相似名称或俱乐部自动合并。

本地只读预览可添加 `--team-links .local/tournament-team-links.json`，文件为 `[{ "teamId": 2, "name": "AG.AL", "liquipediaUrls": ["https://liquipedia.net/overwatch/All_Gamers", "https://liquipedia.net/overwatch/All_Gamers_Global"] }]`。这只覆盖本地预览的队伍读取，验证名称与占用，不修改线上或本地业务队伍表；正式部署后通过后台保存到数据库，不依赖该预览文件。

可用 `$env:TEAM_LINKS_TEST_MYSQL='1'; node --test backend/tests/team-liquipedia-mysql.test.js` 验证真实 MySQL 的旧表增量迁移、持久保存、旧客户端兼容和并发冲突。测试只创建并清理独立随机测试表。

使用上面的本地 AG.AL 双页面配置启动预览后，运行 `node scripts/verify-team-pages.mjs` 验证巴黎两场比赛的队标与跳转，以及后台链接列表的添加、保存重开、删除和清空。后台写请求在浏览器测试中拦截，不写业务数据；数据库持久保存由独立 MySQL 测试验证。

标准赛季可自动识别来源；特殊赛事只需在赛季配置中保留正确的赛事链接，以及维护原本就需要的站内比赛和队伍身份。不需要按赛事手工录入轮次、赛制图坐标或来源比分。复杂的新模板仍可能需要扩展一次通用解析器，不能保证永远零维护。

轮次标题读取对应分支的表头，来源的资格出口列不作为比赛轮次；绘图深度不决定轮次名称。对阵表头中的 `Quarterfinals`、`Round of N` 按来源列显示“第 N 轮”，避免将含轮空的六队赛误称为八强；明确的半决赛、决赛、季军赛保留。`Decider` 统一使用“种子决定战”，例如“第 1–2 种子决定战”。原始表头保留为 `sourceRound` 供核验，不增加后台配置。积分表的来源颜色仍可随快照保存，但前台不据此标注晋级或淘汰。旧快照中的标题在后台下次成功同步后更新。

## 后台同步、数据库与失败

- `app.js` 在数据库初始化并开始监听后启动独立赛制任务，启动即扫描，之后每轮完成后一分钟再扫描。没有页面访问也会运行；保存赛季配置或创建/修改赛季会唤醒扫描。导入模块、测试和只读 API 进程不会自行启动任务。
- 根据赛季配置的日期范围判断：进行中目标间隔五分钟，未开始或结束七天内一小时，较早结束一天；缺少可解析日期时按赛季状态判断，已结束一天，其他五分钟。一次扫描内同一页面只同步一次，多个赛季共享时采用最快频率。实际开始时间受队列和上游限流影响。
- 全部 API 请求至少间隔两秒，parse 至少间隔三十秒；和已有 roster parse 共用队列。多个赛事同时冷启动时会排队。
- `tournament_snapshots` 以规范化页面的 SHA-256 为主键，共享保存结构化 JSON、来源版本、内容摘要、成功/尝试时间、下次同步时间和错误计数。主、子页及身份查询全部成功后，原子替换完整快照。失败不修改旧快照，按一分钟、两分钟等指数退避，上限一小时；重启后重试状态仍保留。
- 数据库中的同步令牌和可续期租约合并同源并发同步；过期任务可重新领取，旧任务不能覆盖新任务的结果。来源读取期间不占用数据库事务。当前上游限流队列仍属于单进程，多副本部署时仅一个实例启用同步，其他实例设置 `TOURNAMENT_SYNC_DISABLED=1`。
- 新表通过现有的非破坏性 `sequelize.sync()` 创建。后台首次处理来源时，可从旧 `TOURNAMENT_CACHE_DIR`（默认临时目录 `owcs-tournament-cache`）导入完整快照，仅填补数据库空记录，不覆盖已有数据。导入后无需依赖文件，随业务数据库一起备份和恢复。
- 离线导出在读取比赛、队伍的同一个数据库事务中取得来源快照及队伍别名，不读取文件、不访问 Liquipedia。使用当前前端读取无赛事快照的旧数据包时显示“暂无赛事进程”；离线快照不轮询网络。展示 API 的元数据摘要包含赛制内容哈希，重试和单纯检查时间变化不会造成无效的数据版本变化。
