# 队伍与选手身份合并

## 调研结论（2026-09-29）

生产只读核查：`owcs_stats`，MySQL 8.0.46，运行版本 `8d8729b`。
ZAN #28：11 场、37 局、185 条选手统计、韩国第一阶段；ZSG #44：12 场、46 局、230 条选手统计、韩国第二阶段。两者无别名，各有一个不同的 Liquipedia 页面。选择哪一个作为主身份由管理员决定，发布代码不会自动合并这两条记录。

实际链路：Studio 的时间线使用 Matchweb 选手 ID → Matchweb 增量摘要/详情 → Stats 收件箱 → 本地身份解析 → 原始时间线镜像及本地统计 → 实时聚合、站点 API、静态快照。

- 队伍已有 `team_aliases`，同步和赛程使用主名/别名；Liquipedia 阵容导入原先仅使用主名。
- 选手原先只有一个 `players.externalId`，新 ID 可能生成新选手；姓名不是跨系统唯一身份，生产存在 DIYA、MCD、SOAE、YATE 同名记录，不能据此自动合并。
- `matches`、`map_games` 的双方和胜者、`player_stats`、赛季阵容及来源证据均需要迁移。英雄统计通过 `playerStatId` 关联，不应相加或重建。
- `match_polls.team1Id/team2Id/pairKey` 和 `match_votes.teamId` 没有队伍外键，也必须检查；不能只扫描外键。
- 赛季统计当前从原始表实时计算，无旧版聚合表需要重算。时间线 payload、digest、事件 ID 属于上游原始证据，不改写。
- 展示配置不保存队伍/选手主键列表；赛程快照保存来源队伍，在读取时绑定本地身份。静态展示包是快照，需要重新导出才包含合并结果。

## 数据设计

保留目标主键和主要资料；来源名称及别名归入目标，队伍 Liquipedia 页面取并集。选手增加别名表和多外部 ID 映射表，兼容保留 `players.externalId`。外部 ID 映射优先于名字；已知旧 ID 始终回到目标。新外部 ID 命中唯一、已确认的别名且位置一致时，绑定到该选手；仅同主名不足以认领已绑定其他外部 ID 的身份。候选歧义或别名位置冲突时停止该比赛应用，进入现有收件箱重试/错误流程。

增加旧本地 ID 重定向和合并审计。连续合并时压平旧 ID 映射；列表只出现保留身份。合并产生的旧名称必须持续作为别名，不能在普通编辑中删掉后又被同步创建。选手合并后标为人工维护，避免孤儿清理删除映射。

## 执行流程

1. 管理员从队伍或选手列表选择来源，再选择保留目标。
2. 服务端在一致性事务中生成只读预览，列出数据数量、重叠关联、资料差异、别名、外部 ID 和阻断原因，并计算数据指纹。
3. 确认时获取数据库身份写入锁，重新读取并校验指纹；数据变化要求重新预览。
4. 单事务迁移引用、合并阵容/来源证据、保留别名及外部 ID、记录审计、建立旧 ID 重定向，最后删除来源行。任一步失败整体回滚。

身份写入锁覆盖同步应用、手工身份/阵容维护、合并及孤儿清理；投票写入需在锁内重新验证参与身份，避免在合并后写入已删除队伍 ID。读取不需要该锁。

阻断：同一比赛/小局/投票合并后双方相同；同一地图局同时存在两个待合并选手；合并后投票唯一键碰撞；别名与第三身份冲突；出现未纳入迁移的外键。位置/地区等资料差异提示并保留目标，不按名称自动猜测身份。

原始时间线里同时存在双方外部选手 ID，也会阻断合并，即使其中一份统计缺失。后续同步重复出现同一规范选手同样报错，整场事务回滚，并由原有收件箱保留错误与重试任务。

同赛季重复队伍关联和同队重复选手关联取并集；相同来源证据的 active 取 OR、firstSeenAt 取最早、lastSeenAt 取最晚，保留所有其他来源。joinDate 取已知最早值，任一 leaveDate 为空则保留为空，否则取最晚值；原行写入审计。

## 发布与维护

启动迁移仅新增表和回填现有外部 ID，不自动合并任何身份；重复启动应幂等。业务合并仅由受保护的管理 API 发起，公共站点 API 不暴露写入口。审计保存执行前资料和引用，用于核查；不提供一键撤销，因为合并后还可能有新同步和投票，恢复需维护窗口、数据库备份及审计对照。

发布前使用独立本地测试库验证真实 MySQL 事务、唯一约束、指纹过期、失败回滚、连续合并、同步重放、阵容证据、投票和旧链接。生产执行前备份数据库，确认保留方向并重新预览。此次开发不自动部署或修改生产身份。

## 管理入口与接口

- 后台「队伍管理」「选手管理」卡片的「合并」按钮；选择保留目标，预览后勾选已核实身份及方向，再执行。
- 选手编辑支持别名；队伍和选手历史档案展示别名、选手全部已绑定的 Matchweb ID 和最近 50 条合并审计摘要。
- `POST /api/teams/:sourceId/merge/preview`、`POST /api/players/:sourceId/merge/preview`，请求 `{ "targetId": 28 }`。
- `POST /api/teams/:sourceId/merge`、`POST /api/players/:sourceId/merge`，请求 `{ "targetId": 28, "fingerprint": "预览返回值" }`。
- 相同指纹重试返回原审计编号；过期数据返回 `409 MERGE_PREVIEW_STALE`，阻断冲突返回 `409 MERGE_CONFLICT`。应用失败时审计也随事务回滚。
- `/api/*/:id/admin-context` 只返回审计摘要；逐行 before-image 留在受保护的 `entity_merge_audits.before`，不向公共 API 暴露。
- 主目录输出 `aliases` 和 `mergedIds`，旧详情与筛选 ID 解析为保留 ID。`/data/v1` 的选手目录和阵容增加可选 `aliases` 字段，名称搜索覆盖确认别名。
- 站点 API 短缓存有正常过期窗口；元数据 revision 已纳入选手别名和重定向表。静态包须重新导出，已分发的旧离线包无法原地改变。

## 验证与运维

运行 `npm test --prefix backend`、`npm run test:static-export`、`npm run build`。MySQL 验证用：

```powershell
$env:ENTITY_MERGE_TEST_MYSQL = '1'
node --test backend/tests/entity-merge-mysql.test.js
```

该测试仅允许 `backend/.env` 指向本机 `localstats`，为所有模型和外键创建随机 `em_<随机串>_` 前缀的隔离表，结束后仅删除本次表；不运行应用初始化或自动同步。可先启动本地 Vite，再设置 `ENTITY_MERGE_BROWSER_URL=http://127.0.0.1:8094`，验证真实 HTTP 操作、1440/390 布局、冲突拦截和旧链接。截图和报告位于 `.local/entity-merge-qa/`。

发布 CI 已加入同一 MySQL 测试：同时提供 `OWCS_ISOLATED_MYSQL=1` 和 `DATA_API_TEST_DB_PORT` 时，仅使用 `DATA_API_TEST_DB_*` 连接隔离实例，创建唯一的 `owcs_identity_merge_test_<进程>_<时间>` 临时库并在结束后清理，不读取应用 `.env`。

本次本地验证：后端 201 项通过、5 项独立 MySQL 环境测试按默认条件跳过；合并 MySQL/浏览器专项 9 项通过（包含真实事务和桌面/手机管理操作）；静态快照 20 项通过；完整构建、API 静态包构建及内嵌资源校验通过；OpenAPI 的 42 个操作、8 份示例及 14 个非法案例校验通过。CI 配置已加入工作区，尚未推送执行；生产仅做只读调查。

生产升级顺序：备份 → 停止旧版本写入进程 → 新版本启动建表和幂等回填外部 ID → 检查健康与预览 → 管理员选择保留方向并执行 → 检查合并审计、统计总量、下一轮同步与公开页面 → 导出新静态包。不能让不认识身份锁和多 ID 映射的旧版本与新版本同时写入。若公共 API 使用逐表授权的只读账号，补充 `player_aliases` 和 `entity_redirects` 的 SELECT 权限。

一旦执行业务合并，回退旧版应用不能作为数据恢复方式：旧版同步不认识已转移的外部 ID，可能重新创建重复记录。先停止所有写入，用备份和审计确定恢复范围；合并后已有新比赛/投票时需要逐项核对，不能直接反向替换全部主键。
